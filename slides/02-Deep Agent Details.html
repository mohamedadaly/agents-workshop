01 · TOOLS

Tools You Can Read

tools = SQLTools(db=db, llm=llm).get_tools()

     + [duckduckgo_search]

No SQLDatabaseToolkit. Each tool is a plain function or bound method — ModelTools reads its name, signature, and docstring to build the same JSON schema a BaseTool’s .args_schema would have carried:

{"type": "function", "function": {

  "name": "sql_db_schema",

  "parameters": {"properties": {"table_names": {"type": "string"}}}}}

01 · TOOLS

The SQLTools Class

class SQLTools:

    def __init__(self, db, llm):

        self.db = db

        self.llm = llm

    def sql_db_list_tables(self): ...

    def sql_db_schema(self, table_names): ...

    def sql_db_query_checker(self, query): ...

    def sql_db_query(self, query): ...

    def get_tools(self):

        return [self.sql_db_list_tables, self.sql_db_schema, ...]

db/llm stored once on self, instead of four separate closures each capturing their own copy. get_tools() hands back the bound methods themselves — ModelTools reads a bound method exactly like a free function, since self was already filled in when self.sql_db_schema was looked up.

01 · TOOLS

One Tool, Read End to End

def sql_db_schema(self, table_names: str) -> str:

    """Get the CREATE TABLE statement and sample rows.

    Args:

        table_names: A comma-separated list...

    """

    names = [n.strip() for n in table_names.split(",")]

    return self.db.get_table_info_no_throw(names)

Just a bound method on SQLTools — self.db/self.llm set once in __init__. No BaseTool subclass, no pydantic args_schema — the docstring and signature themselves ARE the schema source.

01 · TOOLS

The Search Tool

def duckduckgo_search(query: str) -> str:

    """Search the web for something the database can’t answer.

    Args:

        query: What to search for..."""

    with DDGS() as ddgs:

        results = list(ddgs.text(query, max_results=5))

    return " ".join(r["body"] for r in results)

Calls the ddgs package directly — the same library LangChain’s DuckDuckGoSearchRun wraps — instead of going through a LangChain tool class. A module-level function, not a method: it needs no db or llm, so there’s nothing to store on self — and ModelTools reads it exactly the same way it reads a bound method.

01 · TOOLS

The ModelTools Class

class ModelTools:

    @staticmethod

    def schemas(tools: list) -> list[dict]:

        return [ModelTools._tool_schema(t) for t in tools]

    @staticmethod

    def _tool_schema(tool) -> dict: ...

Two static methods, no instance state. schemas() is just a map over _tool_schema() — one call per tool in the list (next slide). Static because nothing here depends on a particular db, llm, or conversation — it’s pure introspection of the function object itself.

01 · TOOLS

Docstring → JSON Schema

ModelTools._tool_schema() splits the docstring at "Args:", reads parameter names via inspect.signature(), and assembles this — verified by actually running it on sql_db_schema:

{"type": "function", "function": {

  "name": "sql_db_schema",

  "description": "Get the CREATE TABLE statement...",

  "parameters": {"type": "object", "properties": {

    "table_names": {"type": "string", "description": "..."}

  }, "required": ["table_names"]}}}

The exact shape Ollama’s chat API expects in its "tools" list — and the exact shape convert_to_openai_tool (what the real bind_tools() calls internally) produces for the same function.

02 · MEMORY

A Plain Dict, Not a Checkpointer

class InMemorySaver:

    def get_messages(self, thread_id): ...

    def append(self, thread_id, message): ...

    def seed_system_message(self, thread_id, prompt): ...

A {thread_id: [messages]} dict — the same role 01’s LangGraph InMemorySaver plays, with the checkpoint machinery stripped away. DeepAgent reads and writes through it exclusively — get_state(thread_id) is the only thing the app itself touches.

02 · MEMORY

Three Methods, Three Jobs

get_messages

Returns a thread’s list, creating a new empty one via dict.setdefault the first time it’s seen.

append

The only sanctioned way to add a message — everywhere in DeepAgent goes through this instead of mutating the list directly.

seed_system_message

A no-op once the thread has any history; otherwise prepends the system prompt as its very first message.

Together: a brand-new thread_id gets seeded once, then every turn just append()s — get_messages() always reflects the full conversation so far.

One thread_id, Every Turn

thread_id = st.session_state["thread_id"]

prior_len = len(agent.get_state(thread_id))

answer = agent.invoke(question, thread_id, max_steps)

trajectory = agent.get_state(thread_id)[prior_len:]

Same thread_id on every turn — invoke() seeds the system prompt once, then keeps appending to that thread’s list. A fresh uuid4() on Clear Chat starts a brand-new thread — the old one just becomes unreachable, the same way rotating 01’s LangGraph thread_id does.

03 · DEEPAGENT

Assembling DeepAgent

class DeepAgent:

    def __init__(self, model, tools, system_prompt, checkpointer):

        self.llm = model

        self.tool_schemas = ModelTools.schemas(tools)

        self.tools_by_name = {t.__name__: t for t in tools}

        self.system_prompt = system_prompt

        self.checkpointer = checkpointer

Same (model, tools, system_prompt, checkpointer) shape create_deep_agent takes in 01 — no RunnableBinding, no LangGraph compile step. Just four plain attributes invoke() reads from directly.

03 · DEEPAGENT

How the Model Actually Sees It

self.checkpointer.seed_system_message(thread_id, self.system_prompt)

self.checkpointer.append(thread_id, HumanMessage(content=question))

messages = self.checkpointer.get_messages(thread_id)

 

ai_message = self.llm.invoke(messages, tools=self.tool_schemas)

The system prompt isn’t a separate parameter to invoke() — it’s the first message in the thread’s own history, seeded once. tools=self.tool_schemas is passed explicitly on every call — no persistent binding. messages already carries the system prompt, every prior turn, and this turn’s question, so the model sees its full context plus its tool menu in one list and one kwarg.

03 · DEEPAGENT

get_state(): Reading, Not Owning

def get_state(self, thread_id: str) -> list:

    return self.checkpointer.get_messages(thread_id)

DeepAgent doesn’t store the conversation itself — the checkpointer does. get_state() is the one sanctioned read, so the app never has to know agent.checkpointer exists. Streamlit uses it to slice out each turn’s trajectory — the same role 01’s agent.get_state(config).values["messages"] plays.

03 · DEEPAGENT

invoke(): The Loop, Spelled Out

for _ in range(max_steps):

    ai_message = self.llm.invoke(messages, tools=schemas)

    checkpointer.append(thread_id, ai_message)

    if not ai_message.tool_calls:

        return ai_message.content

    for call in ai_message.tool_calls:

        result = tools_by_name[call["name"]](**call["args"])

        checkpointer.append(thread_id, ToolMessage(result, ...))

No LangGraph node graph — just a for loop. Thought (model call) → Action (tool dispatch) → Observation (ToolMessage appended) → repeat, until the model answers without a tool call or max_steps runs out.

03 · DEEPAGENT

Dispatching a Tool Call

for tool_call in ai_message.tool_calls:

    tool = self.tools_by_name[tool_call["name"]]

    result = tool(**tool_call["args"])

    checkpointer.append(thread_id, ToolMessage(

        content=str(result), tool_call_id=tool_call["id"]))

tool_calls comes back as a list of {name, args, id} dicts — tools_by_name looks up the right plain function and calls it with **args, same as calling it directly in Python. The result is tagged with tool_call_id so the model can match it back to its request.

@mlflow.trace(name="DeepAgent.invoke", span_type="AGENT")

def invoke(self, question, thread_id, max_steps):

    ...

Without it, mlflow.langchain.autolog() starts a new top-level trace at every self.llm.invoke() call inside the loop — there’s no LangGraph Runnable here to nest them under, unlike 01. Confirmed by actually checking: a 3-tool-call question logged 3 separate root traces before this decorator, 1 trace with 3 nested spans after. One parent span per turn, not per model call.

04 · COMPARE

Framework vs. Explicit

01 · deepagents

Tools — SQLDatabaseToolkit.get_tools()

Binding — model.bind_tools(tools)

Loop — compiled into a LangGraph graph

Memory — LangGraph InMemorySaver + thread_id

Tracing — automatic, nested under one graph trace

02 · Explicit

Tools — plain functions, read by ModelTools

Binding — model.invoke(messages, tools=schemas)

Loop — a plain Python for loop

Memory — a hand-rolled InMemorySaver dict

Tracing — manual @mlflow.trace on invoke()

Same shape, same ReAct pattern — 01 gets there faster, 02 makes every step visible.
